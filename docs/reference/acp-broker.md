# Optional ACP broker (experimental)

Native tmux launching, discovery and bounded log/pane observation remain the default. Nothing installs or migrates an existing agent automatically. The launcher offers **Native tmux (default)** and an explicit **ACP broker · Claude** and **ACP broker · Codex** options. ACP brokers appear in the regular agent list with an ACP badge and open a chat in the ordinary detail panel. The separate experimental catalog is retired. Native transport/outbox/ticket-run launching remain unchanged.

The current implementation supports Linux agent hosts with /proc/pidfd and new Claude or Codex ACP v1 conversations, via an already installed `claude-agent-acp` or `codex-acp` executable. It has no native provider TUI, general resume launcher, model override, project venv, pre-trust, ticket-run launching, attachments or automatic approval. Card names/notes/colors/pinning, ticket context capture, notification/mute and exact-revision read metadata are shared with native agents; chat, permissions and delivery receipts stay ACP-specific. Those must not silently fall back to native input. The basic terminal interface is CC's, not Claude's original terminal UI.

## Integrated launch and chat

Select ACP in **Start agent**, choose a shared machine/project or literal directory, optionally enter an initial prompt, then click **Start Claude (ACP)** or **Start Codex (ACP)**. There is no separate Prepare click: the launcher checks the directory/installed adapter and obtains the same one-use grant internally. Unsupported native-only settings are hidden, not silently translated to flags. Fresh launch defaults to native; a pending ACP launch can reopen its recovery controls.

Before launch IO, the browser persists the original broker UUID and stable endpoint fingerprint. **Check launch** reads that original broker and never repeats creation or the initial prompt. After a backend restart it may refresh the runtime revision only after checking the stable endpoint still matches. The optional initial prompt uses the broker UUID as its message receipt ID; the broker redacts launch-intent text to hash/length before ACP IO, then submits once after successful initialization. An uncertain outcome is inspected, never replayed.

Queue discovery checks the managed broker directory through a bounded per-host helper, verifies process/start/boot, private socket and exact tmux membership/tty, and returns at most32 compact observations within a time budget. Snapshot parsing happens remotely; chat text is not copied into the queue. Existing prototype brokers are read compatibly, without restarting or replacing them. Sources remain explicit: ACP state comes from the verified broker, not pane silence or project logs. Native panes cannot become ACP just because a title or folder matches.

The selected ACP conversation uses SSE, sanitized Markdown, tool activity and exact permission option labels/scopes. Hidden workspaces/compact list views disconnect their selected stream. Streaming edits update only changed message DOM and preserve drafts, reading position and pending approval focus. A card selection does not focus the composer. Messages are sent only when ACP is Ready; busy drafts are retained with an explicit unsupported-queue notice. There is no native keystroke fallback.

Draft and uncertain-action holds use stable endpoint/broker-process scope, surviving runtime connection-revision changes. Recent broker history is bounded in memory; older log pagination is not implemented. **Details → ACP message receipts / Check ACP delivery** exposes durable phases separately from native outbox Submitted/Seen semantics. **All outboxes** remains the native outbox, not an aggregate of ACP receipts. Attention/read state is metadata-only and scoped by endpoint, broker process and conversation; existing replies baseline as read, and only explicitly opened visible recent replies acknowledge their exact observed cursor. Notifications use the actual ACP reading position and per-process mute state.

**Close agent** reviews machine/project, stable tmux target, broker UUID and instance with Cancel focused. The helper persists a close receipt before signaling the exact start/boot-verified broker through a pidfd. It stops the broker's own agent process; it does not kill other panes or complete tickets. Lost responses are checked through the receipt endpoint even after process exit. Duplicate close UUIDs return the durable receipt without signaling again. **Restart & update broker…** directly resumes an idle Claude/Codex ACP conversation with current deployed broker code, as described below. No new conversation is invented as a restart.

## Process and transport

```
CC browser -- REST + SSE -- Rust backend -- existing SSH/ProxyJump -- helper
                                                                      |
                                                            private Unix socket
                                                                      |
remote tmux pane: terminal chat + broker -- ACP v1 JSON-RPC/stdio -- adapter/Claude
```

The broker is installed only for an explicit prepared launch, under `~/.cache/command-center/acp/<launch-UUID>/`. Its tmux pane owns it; it owns the ACP adapter/agent process group. It remains usable through direct tmux attachment when CC, its browser or SSH disconnects. CC reconnects through its existing transport to the broker's private Unix socket. No new network port or remote account daemon is installed. This optional persistent broker is an explicit exception to native mode's short-lived-helper architecture.

SSE uses one persistent shared-transport SSH helper, not repeated log/pane polling. The broker coalesces ACP updates into at most ten bounded snapshots per second per viewer; a quiet connection gets a ten-second heartbeat snapshot. A slow client is bounded/timed out. Losing a watcher terminates only that watcher, never the broker/agent. Reconnection returns current state and bounded in-memory history. Broker failure is different from CC failure: there is no automatic broker or conversation restart, and no pending input replay.

Only process-linked native ACP messages supply chat/activity. Thought chunks are discarded. Tools show bounded title/kind/status; permission cards retain the original bounded tool request and exact option IDs, labels and scopes. Unsupported client RPC capabilities fail closed. No filesystem or terminal capabilities are advertised to the adapter; the Claude adapter can execute its own tools under its normal permission policy. CC never adds skip-permissions or edits trust files. Reply/read positions come from completed prompt receipt order, not token-chunk sequence; new permission identities advance attention even when the agent remains in the approval state.

## Guards and receipts

- Preparation checks canonical directory identity and installed adapter executable identity. The server binds host connection revision and broker UUID in a 120-second single-use grant.
- Start consumes the grant, serializes endpoint edits, rechecks directory/adapter, then exclusively creates a private UUID directory and durable intent before detached tmux creation. No arbitrary executable/flags from the browser. A lost launch response is checked by that same UUID in the inventory, not retried.
- Home/cache ancestors must be owned, not writable by other users, and not symlinks. Managed directories/files are private. Live metadata verifies owner, boot ID, broker PID/start time and command-line path; socket type/owner/mode and peer UID are checked. No TCP broker listener.
- Mutations require the exact broker instance UUID. Permission answers additionally bind the current permission UUID/revision and exact offered option. Both browser and terminal use the same serialized dispatcher; a second client cannot answer an already consumed request.
- Remote SQLite (FULL synchronous) persists UUID, payload digest, action type, phase and timestamp **before** ACP IO. Duplicate UUIDs return the existing receipt; conflicting payload reuse is rejected. Claimed/uncertain receipts never replay. Submitted means written to ACP; Completed means its prompt response completed, not a claim about every side effect. There is no native-log Seen receipt in this preview.
- Browser recovery records contain opaque target/receipt IDs, not prompt contents. A failed/uncertain send retains the draft and blocks further submission until receipt observation resolves it or the human explicitly clears the local hold after checking. Clearing does not resend anything.

Bounds: 64 broker records/host, 16 CC streams globally, 8 socket clients/broker, one active prompt (busy prompts are rejected, not queued), 12,000 UTF-8 bytes/prompt, 1 MiB wire frames, 128 history messages with ~256 KiB total message storage, 100 tool summaries, 8 pending permissions with 16 KiB original tool requests, 512 durable receipts per broker. History is memory-only; native provider logs remain under provider ownership. Old directories are retained rather than automatically deleting possible recovery evidence. `/quit` closes the broker's own agent process group; no automatic cleanup of unknown directories or existing agents.

## Terminal interface

Attach to the returned dedicated `cc-acp-<UUID>` tmux session. Type a line and Enter to send a prompt. `/status` reports state/session, `/cancel` cancels the active turn, `/approve REQUEST_UUID OPTION_ID` answers one displayed permission, and `/quit` terminates this broker and its agent. Permission options print their exact IDs, labels and kinds. Plain Ctrl+C requests cancellation rather than killing unrelated tmux sessions. This preview is a basic line UI, not a full TUI editor.

## API

All routes are under `/api/v1/hosts/{host}/acp`; see OpenAPI. Existing Host/Origin controls apply; every mutation requires the configured exact Origin. Read routes require current `connection_revision`. POST `prepare` takes that revision plus literal project `path` and optional `provider` (`claude` or `codex`, default `claude` for backwards compatibility); provider and executable identity are bound into the grant; POST `start` takes the returned token and optional `initial_prompt` (up to12,000 UTF-8 bytes). GET the base lists managed brokers; GET `/{broker}` reads its snapshot; GET `/{broker}/events` additionally requires `instance` and streams `snapshot`/`unavailable`. POST `/{broker}` takes connection_revision, instance, a fresh action UUID and one of:

- `{action:"prompt",text:"..."}`
- `{action:"permission",permission:UUID,revision:UUID,option:EXACT_OPTION_ID}` — an explicit human decision only, never coordinator auto-approval.
- `{action:"cancel"}`
- `{action:"close"}` — explicit reviewed lifetime control, with a durable receipt and pidfd target check, not a provider ACP method.

GET `/{broker}/receipts?connection_revision=...&instance=...` reads at most40 latest receipt records without requiring a live process; it never retries a command. Card metadata uses the existing `/agents/card` API with an explicit optional `acp` broker UUID and a namespaced64-hex card-instance digest, plus exact tmux target and endpoint revision. Provider/raw broker instance UUID remains separate for ACP commands.

The trusted-network boundary is unchanged; actor claims are not authenticated multi-user identities. Do not run a second backend against production config/state to test this mode.

## Adapter setup and evidence

The broker does not install dependencies. Codex/Claude mode switching can offer a separate reviewed missing-adapter installer (below); ordinary launches still require an adapter already present. It discovers `claude-agent-acp` on PATH or the isolated prefix `~/.local/share/command-center/acp-adapters/claude/node_modules/.bin/claude-agent-acp`. An operator can explicitly install a pinned adapter there without changing their global native Claude. The adapter uses its existing supported authentication on that machine; CC does not provision credentials.

Protocol references: [ACP v1 transports](https://agentclientprotocol.com/protocol/v1/transports), [prompt turns](https://agentclientprotocol.com/protocol/v1/prompt-turn), [Claude adapter](https://github.com/agentclientprotocol/claude-agent-acp). Validation evidence belongs in task0077, including the actual tested adapter version and remote cleanup result.


## Codex adapter

Codex uses the maintained [agentclientprotocol/codex-acp](https://github.com/agentclientprotocol/codex-acp) adapter (`@agentclientprotocol/codex-acp`), which launches a compatible Codex App Server. The older zed-industries package has moved; use the maintained package for new installs. CC discovers `codex-acp` on the target PATH or `~/.local/share/command-center/acp-adapters/codex/node_modules/.bin/codex-acp`. It never installs or invokes npx during launch and never replaces the native Codex executable. An operator can install a pinned adapter into that isolated prefix explicitly.

Existing target-side authentication/configuration is used; CC does not log in or add approval/sandbox overrides. No ACP filesystem/terminal client capabilities or optional extensions are advertised. Ordinary ACP text turns, tool summaries and explicit permission choices share the tested broker path. Native Codex history/session IDs are not used to infer ACP identity. Codex ACP restart uses the guarded same-conversation path below. Steering and model/config selection remain unsupported; reported context usage is described below. Missing adapter/authentication fails visibly without falling back to native or repeating a prompt. Fixture coverage does not establish a real Codex adapter/version certification; that requires a separately approved disposable real-provider test.


## Switching Codex or Claude connection mode

Codex and Claude offer **Switch connection mode…** in the card context menu and the chat **Details** panel. On touch devices, open the agent, tap **Details**, then **Switch connection mode…**; ACP chats expose the same action for returning to native mode. Review the exact native session UUID, folder and destination; Cancel starts focused. Native→ACP uses the installed adapter's advertised ACP v1 `session/load`, never `session/new`; ACP→native uses the validated installed `codex resume UUID` or `claude --resume UUID`. Both retain the original tmux session/window/pane and directory. Native remains the default for ordinary launches.

Definite preflight rejection is recorded as `not_sent`; only a fresh explicit review can try again. Uncertain outcomes remain held for inspection.

The source must be process-verified Ready, with no pending permission or unresolved message/answer receipts. ACP session IDs must be canonical native thread UUIDs independently confirmed against a persisted provider transcript in the source's provider home. Destination executable/directory identity is checked before and immediately before replacement. Card name/notes/color/pin carry over only after exact replacement/conversation verification. Existing ticket launch receipts remain historical records for the original process; no ticket is launched or completed by switching. Machine/tmux/directory/conversation context stays the same; capture the new process explicitly when updating ticket context. Old drafts/outbox entries remain scoped to their original process and are never resent.

ACP→native requires the broker's handoff capability. Older running brokers are not patched or restarted automatically and reject before mutation. A handoff freezes dispatcher input under its lock, persists its receipt before stopping its own adapter group, then the helper stops the exact broker through pidfd. Native→ACP stops/replaces the exact source pane process through guarded tmux respawn. The sibling panes and dimensions are preserved. A brief terminal replacement is explicit in the review; it affects other attached viewers of that pane.

`GET /hosts/{host}/agents/connection-mode` prepares a120-second durable receipt using `AgentModeTarget`. `POST` to the same path consumes `{id:UUID}` once. `GET /hosts/{host}/agents/connection-mode-status?id=UUID` only verifies the original attempt; it never launches or replays. A stable endpoint check permits recovery after backend restart. Browser recovery retains opaque receipt IDs, not prompts. Replacement failure leaves the pane's error visible with remain-on-exit and the receipt for inspection; there is no automatic native fallback, fresh conversation or retry. Pi and summary-based new-conversation handoffs remain unsupported. Fixture results do not certify a real adapter/harness version; disposable real-provider checks need separate authorization.


## Install a missing adapter during a mode switch

If no supported ACP executable is found, **Switch connection mode…** offers **Install adapter and review switch**. The review names the fixed package and private per-user prefix: `@agentclientprotocol/codex-acp@2.7.0` for Codex, or `@agentclientprotocol/claude-agent-acp@0.107.3` for Claude. Claude requires Node.js 22 or newer, checked before installation; CC does not upgrade Node. Opening/cancelling the review installs nothing. Existing PATH/managed adapters are reused; incompatible adapters or an existing incomplete managed folder are not replaced or repaired silently. Node.js/npm must already be present on the target Linux machine.

The explicit install click consumes a120-second, endpoint/source/manifest-bound receipt before shared-transport IO. It starts a private one-shot installer, not an agent or host daemon, with no new port. Only the fixed package/version/registry and SHA-512 integrity are allowed; clients provide only the receipt UUID. npm runs in an isolated staging directory with lifecycle scripts, audit/fund and project/user/global npm configuration disabled. The installed package and executable are validated before Linux atomic no-overwrite publication into `~/.local/share/command-center/acp-adapters/<provider>`. No global package installation, native harness update, credentials change or agent stop occurs. The package may include its compatible Codex dependency inside that prefix.

Install jobs have a180-second runtime budget, a768 MiB monitored job-disk budget, private atomic result receipts and a per-provider exclusive lock. Failed staging/cache trees are cleaned when still safely owned. At most128 receipt entries are retained. Existing/incomplete/uncertain jobs are not overwritten or automatically retried. Unsupported atomic publication or separate staging/destination filesystems fail safely. npm output is not surfaced or persisted; failures report bounded operational reasons.

The dialog can close while installation completes; its opaque local receipt ID restores **Check progress**, including after browser or backend restart. Status checks verify the original stable endpoint and never start an installer. Successful installation triggers fresh source/process/directory/adapter/screen checks and a separate **Switch to ACP** review/confirmation. If the agent changed, became busy or has unresolved messages, the adapter stays installed and the switch is rejected. General/native launching remains unchanged. Pi installation and automatic adapter updates are outside this slice.

API: `GET /hosts/{host}/agents/connection-mode` may return `install_required` plus an `installation` proposal. `POST /hosts/{host}/agents/connection-mode-install` consumes `{id:UUID}` once. Read `/connection-mode-status?id=UUID` for `installing`, `installed`, `install_failed` or `install_uncertain`. Installation receipts cannot be submitted as switch receipts. A successful status response includes the current runtime revision only after stable endpoint verification, enabling a fresh preparation after service restart. Missing responses retain the original ID; neither installation nor switching is repeated automatically.

Claude handoffs preserve `CLAUDE_CONFIG_DIR` and require a process-linked persisted native conversation. Validated native continuation records resolve compacted conversations; project recency or a guessed UUID never establishes identity. Active or unverified background tasks and pending ACP tools block handoff. Adapter session loading must return the requested UUID; failures never create a replacement conversation.

Adapter JSON-RPC frames are bounded at 8 MiB to accommodate historical image replay during Claude session/load. Non-text image payloads remain excluded from broker chat/snapshots and are not persisted by CC. Client snapshot/event response limits stay at 1 MiB. Oversize adapter frames fail closed with a specific replay-limit error; no session/new fallback or automatic retry occurs.

## Resolve an earlier switch after native recovery

If a native-to-ACP attempt failed and the human separately restored the original native conversation, the old checking receipt can be resolved explicitly with **Resolve recovered switch** in its status dialog. POST `/hosts/{host}/agents/connection-mode-recover` takes `{id, target}` where target is the current native AgentModeTarget. It verifies stable endpoint and exact original tmux target, a different process linked to the original persisted conversation (validated Claude continuation allowed), and that the original broker and adapter have exited. It sends no keys, stops/restarts nothing and never retries a switch. The receipt retains the original plan plus recovery process/session/time metadata and becomes `recovered`, rather than claiming successful switching or no mutation. Other unresolved message/answer receipts remain barriers.

A recovered status clears that browser's obsolete receipt reference and prepares a fresh review; **Switch to ACP** remains a separate explicit confirmation. A live old broker/adapter, wrong/stale process, unrelated conversation, target or endpoint fails closed. Install receipts and ACP-to-native attempts do not qualify. Coordinators must not resolve uncertain attempts without an explicit human recovery request.

GET on the recovery route performs read-only discovery of a unique unresolved native-to-ACP receipt for the exact current target, and verifies native recovery before exposing it. This supports another browser or cleared local storage without resolving anything. Both GET and POST repeat endpoint/process/conversation/old-process-exit guards; only the explicit POST writes the recovered audit metadata.

## Busy-time prompt FIFO

New brokers advertise `prompt_queue` for the loaded session. Explicit prompts can be accepted while Ready, Working or Approval, but only one `session/prompt` is active. Follow-ups stay in a private SQLite queue bound to that broker instance and exact session; they are not live steering and the provider does not receive them until the previous turn completes. Permission dialogs remain explicit human decisions. Queued intents survive browser/backend disconnect while the tmux broker runs.

Limits:16 queued prompts,12000 UTF-8 bytes each,24h expiry, existing512 metadata-receipt cap. Text is kept only as pending intent (not a separate transcript), secure-deleted before the durable claim/adapter IO and on cancellation/expiry. Queue admission is durable before acknowledging `queued`. Completion advances FIFO only after the active receipt completes, with no permission or unresolved/uncertain send barrier. Failed/uncertain delivery holds later prompts; `queue_blocked` labels that state. A new broker instance never replays old queued intents; startup marks them blocked and discards payloads only after exclusive broker ownership.

`cancel_queued` takes a queued prompt UUID and a new command UUID. It cancels only an unsent intent; dispatch wins under the same lock, so a prompt already claimed requires the separate active-turn Cancel action. Cancel turn affects only the active turn; previously queued explicit follow-ups remain and can run after it ends. Explicit Close warns and cancels remaining queued entries before stopping the adapter. Receipts distinguish queued, claimed, submitted, completed, cancelled, expired, blocked and uncertain. Duplicate UUIDs return original metadata without IO. Queue/receipt-only recovery never retries delivery.

Chat uses one stable bubble per accepted prompt, with queued/submitted/held states and cancel-before-dispatch. Lost acknowledgements reconcile against the original receipt/snapshot; confirmed queue-full rejection keeps the draft and introduces no false uncertain-delivery barrier. Existing live brokers missing the capability keep busy sending disabled. Deployment does not hot-patch or restart them; using this feature on an existing broker needs a separately authorized replacement/resume. No blanket permission, native fallback, auto-start or auto-resend is added.

## Context usage events

New brokers consume session-scoped `usage_update` events as current context occupancy (`used`) and capacity (`size`). Nonnegative safe integer counts are accepted (positive capacity), zero usage and lower counts after compaction replace prior values rather than accumulating. Missing/invalid fields stay unknown; model names never imply a capacity. Unknown/binary/thinking/tool payloads and cost metadata remain excluded. The recognized Claude model tag may supply only a bounded model identifier.

Snapshots/SSE/inventory carry numeric usage metadata and process-linked `AgentTokenMetrics` for the existing card/chat context meter. Receipt time is retained without refreshing it on polling; disconnected/failed observations are stale. Usage changes neither activity state nor unread/reply receipts. Context-only reporting leaves all cumulative session token totals null and does not add to Settings token accumulation. Older brokers without usage data show Usage unreported; no native-log scan, automatic /usage prompt, hook, restart or estimated backfill is performed. Supporting brokers report values only when their adapter emits usage_update; an idle resumed conversation may stay unknown until an event arrives.

## Explicit local commands

Native harness shell mode and CC broker execution are different operations. Stock Claude/Codex ACP adapters expose no client operation for native no-model `!command` execution; their snapshots report `harness_commands:false`. The optional CC Codex extension below adds an explicit negotiated native path. Without that capability, leading `!` in ACP chat disables ordinary submit/Enter and shows the limitation. It does not execute through the broker or silently become a model prompt. Use native connection mode for the harness terminal feature. Pi's native terminal commands are unchanged; its separate RPC protocol is not automatically enabled.

New native-host brokers advertise `local_commands` only for explicitly separate **Run via CC broker** execution. That optional button names the machine/directory and states that output is outside the harness conversation. **Send as chat** explicitly sends the original text to the model instead. Older brokers without the capability disable broker execution. Current UI labels command/output as CC broker content even for older receipts. New broker receipts additionally record `execution:"cc_broker"` and `context_included:false`. In the broker's tmux terminal, `!command` is refused without execution/model input; `/broker COMMAND` explicitly invokes separate broker execution. Existing live brokers require an authorized restart/update to acquire changed terminal behavior and metadata. Container/profile brokers disable host execution; there is no host-shell fallback for container agents.

`POST /hosts/{host}/acp/{broker}` accepts the existing exact connection revision, raw instance and durable intent UUID, plus `{action:"local_command",execution:"cc_broker",text:"!pwd"}`. The explicit execution acknowledgement and original bang-prefixed text participate in the intent digest. Missing/wrong execution acknowledgement is rejected before transport IO, so older cached bang composers cannot execute by accident. A command shares the prompt FIFO, waits for actual provider Ready, no permission and no uncertain-send barrier, and starts once only after its durable claim. It runs as the broker's account with its inherited environment, in the pinned directory (device/inode checked through an open directory fd), using fixed `/bin/sh -c`, no stdin and its own process group. Clients cannot override the directory, environment, shell or PID. This is explicit human shell execution with account permissions, not a sandbox or model tool call. Coordinators must not use it to bypass scoped instructions or human approvals.

Runtime is limited to120seconds; combined stdout/stderr is bounded to32768bytes while excess is drained. Output is rendered as literal command text, streams into one stable bubble, and finishes with the exit status. It is not sent to the model and never becomes model reply/usage evidence. Snapshots expose `command_running`, `command_id`, `command_timeout` and `command_output_limit`; provider Working/Ready remains independent. Receipts retain metadata only (`exit_code`, `timed_out`, `output_truncated`), not command output or environment. Pending command text uses the same private expiring FIFO and is discarded before execution.

**Stop command** stops the explicit CC broker command and sends `{action:"cancel_command",command:original-command-UUID}` with a new intent UUID. It validates the active command and stops only its owned process group; stale cancellation is rejected before claiming. Queued commands use `cancel_queued`; Close cancels pending intents and stops the running command and adapter. Mode switching is blocked during execution. Lost acknowledgements recover the original receipt without re-execution, including after browser/backend restart; an uncertain outcome is held and never automatically retried. Command output remains bounded in broker memory rather than being copied to a durable transcript.

## Restart and update a broker

Open an ACP agent’s **Details → Restart & update broker…**, or use the same action in its card context menu. The review names the exact conversation and folder; Cancel starts focused. Confirm **Restart & update broker** to replace that pane’s broker/adapter once, directly in ACP mode, loading the existing conversation. This uses the current backend’s bundled broker source, so restarting also picks up deployed broker fixes and capabilities. There is no native-mode intermediate, implicit model prompt, new conversation, package installation or automatic update. It also supports a deliberate restart when the code is already current.

The action requires verified Ready, an independently verified persisted conversation, supported adapter `session/load`, and no pending permissions/tools/commands or queued/unresolved message receipts. Preparation binds endpoint, broker/process start/boot, directory/adapter identities and broker source SHA-256; changes before execution reject before stopping anything. A120-second one-use preparation and durable receipt precede mutation. The old broker’s guarded handoff freezes input and stops only its adapter group; pidfd verifies its exit before replacing the same pane. Siblings, window dimensions and card metadata are retained; drafts/old receipts remain scoped to the old process and are not resent. The short in-memory ACP view may be rebuilt from whatever the adapter replays; persistent native conversation identity is preserved.

API: use the existing connection-mode GET/POST/status endpoints with `AgentModeTarget.mode="acp_restart"` and an exact ACP `broker`/`broker_instance`. Status verifies the replacement session, readiness, handoff marker/process identity and copied broker-source hash before transferring card metadata. Browser reload/backend restart checks the original durable receipt and never re-executes a restart. Unknown outcomes require inspection; no fallback or retry. Container/profile agents are rejected, with no host execution fallback. Source brokers must support the existing handoff capability; unsupported brokers fail closed without process mutation. Deployment alone leaves every running agent unchanged.

## Optional native Codex shell extension

The [versioned adapter extension](../../adapters/codex-native-shell/README.md) targets Codex ACP2.7.0 at a fixed upstream commit. The approved build is installed in p15’s previously absent standard managed Codex prefix; it is not automatically distributed to other hosts or enabled on existing agents. Stock adapters remain unsupported and native tmux remains the default. Claude is not substituted with broker execution; native pi remains unchanged.

A supported Codex adapter advertises the exact `command-center/native-shell` capability version1. Only then does the broker report `harness_commands:true`, `harness_command_scope:"codex_native_full_access"`, and the composer enable **Run in Codex** / Enter for bang-prefixed input. The hint identifies machine/project and full-account native shell access outside the model sandbox. Run via CC broker and Send as chat remain explicit alternatives with different context semantics.

POST the existing ACP command endpoint with `action:"harness_command"`, original `text:"!pwd"`, `execution:"codex_native_full_access"`, durable UUID, broker instance and connection revision. The broker validates current capability/scope, queues with explicit prompts, persists/claims before IO, and invokes only the fixed `_cc/session/shell` method against its own session. It never passes client methods, session IDs, cwd, shell, environment, policy or timeout overrides. Missing/unknown support rejects before claim, with no model or broker fallback.

The adapter calls native `thread/shellCommand` inside its normal serialized lifecycle, observes exact thread/turn and native source=userShell items, and uses the existing native cancellation flow. It sends no model turn/start. Native command/output appear as labeled literal text, not a model answer. CC bounds rendered output to32KiB and native runtime to120seconds (130second result ceiling). Provider-owned output/session context can follow native truncation rules; CC never edits provider transcripts to fabricate context. Receipts record execution owner, exit/truncation and context_included only from matched final native proof; unknown proof is uncertain, held and never replayed. Failed/unsupported native methods fail visibly and block later queue work rather than falling back. Native command receipts do not manufacture model reply/usage evidence.

Browser/backend disconnect leaves the tmux-owned broker/native command alive; reloading reads the original receipt. The adapter also caches512 bounded in-memory native request outcomes, rejects UUID reuse for different intent, and never re-executes identical/failed intents. Durable CC broker receipts remain authoritative across backend restart. Agent/broker restart is explicit and never replays queued/uncertain native work. The human-approved disposable Linux/p15 test passed using the real Codex0.166.0 and patched adapter2.7.0: native execution, persisted native context, cancellation and zero model POSTs. Existing agents were untouched. This does not certify other versions/remote hosts; the reviewed p15 installation/deployment is recorded in task0111. Existing Codex ACP agents need explicit Restart & update broker; other hosts need separate installation. See task0110 for real-test evidence.
