---
name: cc-restart
description: Restart requested Codex, Claude or pi agents in their existing tmux panes and resume verified conversations, including after authorized package updates.
---

Read the coordinator role and repository-root `docs/reference/coordinator-restarts.md`. A clear human restart request, or a maintenance task explicitly including restarts of named agents/a bounded set, authorizes those restarts without another generic permission question. Ordinary messaging/close permission, ticket status, silence or a package update alone does not authorize killing agents. This capability request itself restarts nobody. Keep the coordinator/operator alive unless explicitly included.

Resolve fresh machine connection revision, stable session/window/pane and foreground instance. Require a unique process-linked persisted native conversation. Restart replaces this pane’s shell, agent and children, keeping its window/pane and siblings; active tools/unsaved work may be interrupted. Review actual collateral effects against the request; clarify ambiguity outside delegated scope. Already-dead agents after a reboot require explicit saved-session resume/new launch, not a fabricated restart target.

For updates, finish/verify the authorized package installation first, then request a fresh restart preparation. The backend resolves the currently installed CLI, rather than relaunching the old process image. Review executable path/provider/native session/project/literal command against the request. An upgrade after preparation invalidates its installation identity; never reuse that preview to bypass the check. Package installation is a separate task; cc-restart provides no SSH/shell/package-manager or arbitrary-command execution. Within an explicit maintenance assignment, cc-message can relay the installation task to the authorized machine agent before its restart. A new PID or complete receipt is not version proof; use actual updater/version evidence.

GET `/hosts/{host}/agents/restart` with `connection_revision`, `session`, `window`, `pane`, `instance`. It creates a durable prepared receipt (120-second validity), sends no input. Before one POST persist the opaque receipt ID, CC origin, host/endpoint, original target/process/conversation and local attempted phase privately under ignored `.local/coordinator-restarts/` (directory0700/file0600). Fail closed if it cannot be saved. Keep plans/paths/tokens out of public reports and never invent client flags/model/policy overrides for the fixed resume command.

POST `/hosts/{host}/agents/restart` with only `{id:PREPARED_ID}` and exact Origin, once. `checking` means attempted, not success. GET `/hosts/{host}/agents/restart-status?id=PREPARED_ID` is read-only recovery, including after client/backend restart; it never respawns. Complete proves the exact resumed conversation and restart process marker, and transfers card preferences once. Re-read queue/conversation for the replacement process before future messages. Old drafts/outbox entries stay bound to the old process; never replay/retarget them automatically.

After timeout/lost response/5xx/409 or incomplete verification, inspect the same receipt and original pane; never POST again, allocate a replacement receipt as an automatic retry, close/relaunch as a workaround or downgrade process checks. Report unresolved outcome rather than polling indefinitely. No direct PID kills, tmux/SSH commands, simulated exit/relaunch or automatic native trust/approval answers. Report receipt, machine/target, provider/session, completion evidence and package-version evidence separately. No live restart tests.

Restart preserves and revalidates the observed process VIRTUAL_ENV (when set), adding its bin directory to PATH. A missing/replaced venv requires a fresh reviewed plan; do not source activation scripts, silently drop it, or substitute a new project default. Package updates that change the venv invalidate earlier preparations: prepare after updates, then restart once using the new reviewed grant.
