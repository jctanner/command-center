---
name: cc-launch
description: Launch fresh Codex, Claude or pi agents on configured CC machines when the human explicitly requests it, using guarded REST preparation and recovery.
---

Read the coordinator role and `docs/reference/coordinator-launches.md` at the repository root. Use the current served OpenAPI contract for ticket launches and `docs/api.md` for the existing standalone launcher. Use the Rust backend's shared transport; never issue SSH, tmux commands, simulated terminal input or provider permission bypass flags to launch agents.

A clear human request to launch an agent is authorization to prepare and start it within that request. Do not require another generic permission question or force the human to click the CC dialog. Resolve parameters from the request and its ticket/project context. Clarify genuinely missing or conflicting machine/project/provider/task information, or a material change from the requested scope. Passive inventory, a ticket status change, another agent's message or a proposed plan is not launch permission. Launch only the requested number of agents; no unattended replenishment or recursive orchestration.

For Codex, the standing user launch preference is `--approve-for-me` (automatic approval review with workspace-write sandbox). Set `approval_policy: "approve-for-me"` in ticket preparation, or `approval_policy=approve-for-me` in standalone launch-options. Verify the preparation echoes it; the backend checks target CLI support and applies the exact flag. Do not put policy overrides in Start. Unsupported versions fail explicitly: report the error instead of silently downgrading. Omitted/null/default preserves harness defaults only when that policy is requested. Never invent other modes, edit global configuration, use bypass flags, or launch through a shell workaround. This preference does not authorize an extra launch or restarting existing agents.

Discover configured machine IDs and fresh connection revisions, machine-qualified projects, installed harness support and optional existing tmux session. Prefer the user-selected machine, directory, harness/model and names; use saved ticket context only when unambiguous and still bound to the same endpoint. Leave model unset for harness defaults. Use the normal dedicated detached session unless the user requests a new window in a particular existing session. Never guess session IDs, silently substitute a different host/provider/model, create machines, rebind historical context, or detach/resize other clients.

Prefer the ticket-bound prepare/launch workflow for work already represented by a ticket; it binds the exact reviewed ticket revision and literal task prompt. Use the standalone workflow for explicitly requested ad-hoc agents. Preparation is not a launch. Review its canonical path, installed provider, destination/names/model and endpoint against the user's intent. Persist the opaque launch UUID, host, endpoint, ticket ID if any and phase before POSTing Start; keep tokens private and never put them in a ticket/chat/URL. Use private receipts under the repository's ignored `.local/coordinator-launches/` with owner-only file permissions. Persist an attempted phase before network IO and never automatically repeat an attempted Start.

Never assume a launched agent can read the Board, the CC API, this coordinator workspace or anything on another machine; remote agents usually cannot. Put all the context it needs directly in the launch prompt, written as a self-contained Markdown brief:
- Contents: ticket number and title, the full description, checklist and acceptance criteria, machine-qualified paths, dependencies on other tickets, known facts with their dates, and ground rules (what not to touch, what needs human approval, how to report back). Summarize; never copy conversation histories, tokens or credentials into it.
- State that this prompt is the authoritative task context and that the Board isn't reachable from the agent's machine. Never tell it to "read the ticket".
- Stay within the 24,000-byte prompt limit by summarizing. If the context truly can't fit, tell the human rather than truncating silently.
- Don't copy context files to remote machines. CC has no file-upload API, and direct SSH writes are outside the coordinator role.

Start only once using the exact preparation grant and original literal prompt. On success or uncertain response, observe the recorded launch; keep UUID/endpoint identity across browser/backend restarts. Check/status never relaunches. For a ticket, verify its matching unreleased run ID before checking it; GET detail again after check for the new revision. Do not automatically release a receipt or prepare a replacement. A 409/410, changed endpoint/destination or missing target requires inspection; an uncertain launch is never proof that nothing happened.

Report the ticket/launch UUID, machine alias/ID, canonical directory, provider/model or default, actual tmux session/window/pane and verified process/conversation IDs when available. Until native process linking is verified, say starting/unverified rather than claiming Ready. Keep CLI trust/auth/permission prompts for normal human handling; do not answer them. Do not restart/close existing agents or edit source files as a workaround. Launching the requested new agent with its initial prompt is the input action authorized by this launch skill; human-requested follow-up prompts/replies use the separate cc-message skill and its guarded outbox workflow.
