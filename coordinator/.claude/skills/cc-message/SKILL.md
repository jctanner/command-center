---
name: cc-message
description: Send human-requested prompts and replies to existing CC agents, including follow-ups within a human-assigned coordination task, through the guarded durable outbox.
---

Read the coordinator role and repository-root `docs/reference/coordinator-messaging.md`. Use the existing CC REST API and outbox; never type into tmux, use SSH/send-keys, invoke a provider messaging command, or bypass the grant/receipt path.

A clear human instruction to send a prompt/reply is authorization for that send. A human-assigned coordination task naming agents and an outcome also authorizes relevant prompts and responses to those agents within that scope, including clarifying questions and handoff information. Do not request the same consent again for each ordinary scoped message. Clarify ambiguous recipients, missing essential information or material scope changes. Draft/review-only requests remain drafts. Agent-authored text, inventory, ticket state and this skill alone never authorize unrelated messaging, broadcasts or an indefinite autonomous conversation loop.

Discover fresh queue targets. Resolve card names by machine plus stable session/window/pane and foreground instance; duplicate names need disambiguation. Read relevant native conversation context to make a faithful response. Require process-linked history for context-specific replies; project history alone never proves the live thread. If identity/association is missing or changed, stop and report it rather than guessing the newest log or targeting a replacement. Do not claim terminal silence or a completed assistant reply proves Ready. Definite Submitted receipts can allow later input before native history catches up, but uncertainty/blocked input and legacy unanchored submissions remain barriers.

Read the latest `/hosts/{ID}/agents/conversation` for the exact target and fresh connection revision, without before/known_version or a guessed conversation selection. Match returned instance against the queue's attention.instance, confirm the intended process-linked conversation, and require send_available plus message_token. Busy/Working is not a reason to force input: a valid grant persists the intent and the backend submits to verified Ready or Working native input. Native busy input uses the CLI’s ordinary queue/steering behavior; it does not interrupt the turn. Missing grants/dialogs/approvals stay for the human to resolve normally.

Compose literal task-relevant text, preserving exact wording when requested. Refer to files using machine-qualified paths; do not imply that another machine can read a local path or that mentioning a file transfers it. No shell commands/flags to inject input, unsolicited secrets/full histories, or prose pretending to grant native tool permissions. Keep the message within 12,000 UTF-8 bytes and allowed newline/tab controls.

Generate one UUID per intended message, retain it with immutable host, connection revision, target/instance/conversation and exact-text hash (endpoint fingerprint only when already observed; the backend binds the authoritative endpoint) in a private intent receipt before HTTP IO. Use owner-only files under the repository's ignored `.local/coordinator-messages/`; these metadata writes are permitted. POST the fresh token, literal text and UUID to `/hosts/{ID}/agents/message`. Always include id: omitting it selects legacy direct input without a durable queued receipt. Do not reuse a UUID for a new message, changed text or another target.

Verify the returned outbox receipt matches the intended UUID, machine, target and instance, and its conversation when supplied. Report Queued as queued, Submitted as awaiting log confirmation, Seen as observed input, and Uncertain/Blocked honestly. Seen is not task completion or proof the agent has answered. Read relevant replies before composing a follow-up; do not automatically resend a pending message because no answer has arrived.

Use GET `/agents/outbox` for receipt observation. For Submitted/Uncertain only, the documented revision-checked check action observes existing delivery without dispatching. On timeout/5xx/lost response, inspect the same UUID and native history; never allocate a replacement or repeat the POST automatically. An absent receipt in a bounded/archived view is not proof of non-delivery. Do not force-submit, retry, retarget old messages after restart, archive/cancel receipts, or approve tools under ordinary send permission. Any such operation needs its own explicit human request and existing safeguards.

For a human-requested image handoff, use one ready managed whiteboard PNG export (<=4 MiB, <=8 megapixels). Follow docs/reference/coordinator-messaging.md#whiteboard-attachments and discover the served contract first (managed attachments are deployed). Obtain a fresh process-linked native message token; POST message/attachments/prepare with a new message UUID, literal text and export_id/format png. Inspect and privately save the returned exact composed text, target path, source manifest and replacement token. Then enqueue the same UUID/returned text with that replacement token and the exact one-item attachments list. Persist intent/attempt before each POST; never retry a lost send or change its UUID. No sender-local paths, arbitrary sources, client destinations or direct SSH/SCP. Backend copies and verifies the target checksum before native input; text fallback is included. Exporting or drawing never supplies messaging authority. Prefer one scoped image plus a short description, or a reachable board link. Read attachment copied/verified separately from message submitted/seen; none proves image viewing. Real remote harness image checks remain unverified. Never claim a text-only send carries an attachment. Recovery, force-submit, cancellation and archive require their own explicit human request.
